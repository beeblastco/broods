# apps/cloudflare-worker

Worker behind core's `worker` sandbox provider, the fast Cloudflare V8 Worker: bash in a V8 isolate, no container, no Durable Object. `src/index.ts` is the authenticated `fetch` router; `src/runtime.ts` is what each sandbox's isolate runs (just-bash, a bash in TypeScript with its own in-memory disk); `src/vfs-state.ts` turns that disk into bytes for R2 and back. paths relative to `apps/cloudflare-worker/`.

core's `apps/core/src/harness/sandbox/worker-executor.ts` is the only caller. route shapes are in `apps/docs/docs/internals/sandboxes.md#worker`.

## Gotchas

- **keep it dumb.** reservations, ids, env merging, the working directory and the output limit all come from core; the Worker runs exactly the script it is given. a rule added here is a rule core and its tests cannot see.
- one isolate per sandbox id, loaded with `LOADER` (Dynamic Workers) from `.generated/runtime.txt`, which `bun run build` writes from `src/runtime.ts`. the loader caches by id, and a loaded isolate's network and CPU limit are fixed, so the id carries both. `check`, `dev`, `deploy` and the tests build first; the file is gitignored.
- `exec` answers core's `SandboxExecAnswer` (every field of `SandboxExecResponse` a Worker can fill), the same type the Container bridge answers, so a contract change fails `check` here. the request shape is `WorkerExecRequest` in `contract.ts`, and the zod schema in `index.ts` is typed as it, so the two cannot drift either. the bearer check is `apps/cloudflare-sandbox/src/bearer.ts`, shared with the bridge. `duration_ms` is the host's wall clock around the RPC: inside an isolate the clock only moves on I/O.
- a sandbox's files live in R2 under `sandboxes/<id>` only when the call says `persist`; an ephemeral call runs on an empty disk and stores nothing. the stored bytes are one gzip of a JSON header (paths, kinds, modes, sizes) followed by the files' raw bytes; the shell's own layout, and the working directory while it stays empty, are rebuilt from scratch every time. the runtime packs the disk after each command and answers `"unchanged"` when the bytes match what it was given, so a read-only command ships nothing back and the host writes nothing. what a command wrote before just-bash's deadline stopped it is kept, since the shell still answers; a command the isolate's CPU limit kills answers nothing, so the disk stays as it was before the call. `MAX_STATE_BYTES` caps one object; a disk past it stays as it was and the call answers 413 with what to clean up.
- there is no lock per sandbox. every store is conditional on the etag the disk was read under (or on no object): R2 can only delete unconditionally, so an emptied disk is stored as an empty object instead. of two calls racing on one sandbox the second to finish answers 409 and stores nothing. core runs the commands of one reservation one at a time, so the 409 is a backstop it surfaces as an error, not a path it retries.
- a failure in the runtime or the store answers 500 with its message, so core shows it. `limits.cpuMs` on the loaded isolate is the real guard for a busy single builtin (`awk`, `sort`, `jq`): just-bash's deadline fires only when the shell waits on something, and `Date.now()` does not move while it computes. the text workerd uses for that kill is not matched; a kill reads as the 500. busy shell loops are stopped earlier by just-bash's own caps (100 000 commands, 100 000 loop or `seq` iterations), which answer exit 126 with the cap in stderr.
- just-bash's `maxOutputSize` is a total across both streams and fatal (exit 126, nothing kept), so it sits at 8 MiB and the runtime cuts each stream to the call's `outputLimitBytes` itself.
- `nodejs_compat` on the loaded isolate is for `node:zlib` (just-bash's gzip and file sniffing, and the stored disk) and the `Buffer` global; nothing else from Node is in the browser build the runtime bundles.
- `globalOutbound: null` is the whole network policy when the sandbox has no internet; `curl` is not even registered then. with internet, just-bash's own fetch goes through the isolate's global `fetch`, so the policy is enforced twice.
- `sst deploy` ships one Worker per stage with this workspace's `deploy` script (`deployCloudflareWorker` in `apps/core/sst.config.ts`), named `resourceName("worker")`, when the deploy has `CLOUDFLARE_API_TOKEN`. it reruns only when a file here, `bun.lock`, or a file listed there (`bearer.ts`, the exec contract) changes. every stage shares the one `broods-worker-state` bucket: a sandbox id is unique to its reservation, and production regions share their reservations. a file this Worker imports from another workspace must be added to that list.
- the Worker and core must agree on `WORKER_API_KEY` = core's `CLOUDFLARE_WORKER_API_KEY`. the infra repo generates it and writes it to both; a Worker without it refuses every call. never deploy from a branch or an agent session.
- `bun test` runs the Worker in Miniflare with a real Worker Loader and R2: no Docker, no account. Miniflare does not enforce `limits.cpuMs`, so the CPU kill is never exercised locally. the codec has its own test under Bun.
